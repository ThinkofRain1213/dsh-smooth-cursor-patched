## 条目 C — 空行上的光标被画错一行（✅ 已修复，v0.1.9-patched.6）

**报告日期**：2026-10-13
**修复日期**：2026-10-13（commit `bf2b9db`，tag `v0.1.9-patched.6`，npm 已上架）
**证据等级**：**已由真实 Lexical DOM 实测证实**（修复前后定点对比 + 边界回归）
**影响面**：主聊天输入框（`[data-composer-input]`，Lexical contenteditable）

### 现象（用户描述）

1. 光标停在某行行尾，按 `Shift+Enter` 生成一个空行。按理光标应落在**空行**上，实际显示为落到了**下一行**。
2. 在该状态按 `↑`。按理应回到空行，实际显示为直接到了**上一行**，像"跳过了空行"。

### 根因（已证实，与早期候选机制不同）

> ⚠️ **本节已重写。** 早期版本把根因归为"Case A 越权命中空段落 `<p><br></p>`"。**该机制不成立**——见下方"被推翻的旧机制"。

**真实机制**：Tier 1.5 的 Case A / Case B 都以 `focusNode instanceof Element` 为入口，而真实 DSH 的 `getSelection().focusNode` **永远是 `#text`**（Lexical 把文本包在 `<span data-lexical-text>` 里）。于是：

1. Tier 1 的 `getClientRects()` 在空行边界返回**空**（浏览器对折叠空行选区不给几何）；
2. Tier 1.5 **整个块被 `instanceof Element` guard 挡掉**，Case A / Case B 从不执行；
3. Tier 2 的 `getBoundingClientRect()` **全零**；
4. 落到 Tier 3：`startEl` 是那个多行 `<span>`，而 `<br>` 是它的**兄弟**（`querySelector('br')` 返回 `null`），于是最终取 `startEl.getBoundingClientRect().top + halfLeading` —— **整个 span 的第一行**。

**结果**：光标在 span 内部的第 2、3… 行时，测出来永远是首行 → 彗星画在高一行。实测偏差 **+26px = 24px 行高 + 2px 半行距**。

**为什么"时对时错"**：取决于光标是否**恰好自带 client rect**。有 → Tier 1 命中，正确；无（空行边界）→ 掉到 Tier 3，取到 span 首行。这既解释了"有时对有时错"，也解释了现象难以稳定复现。

### 修复

新增 **Case C**（纯增量 +52 行 / −0 行）：当 `focusNode` 是文本节点、且**自身无任何几何**、且**紧接在兄弟 `<br>` 之后**时，返回 `br.top + lineHeight`——与 Case A 处理元素锚点用的是**同一公式**。`\n` guard 防止光标已在更下方时反向偏低。

详见 [fix-plan-blank-line-caret.md](./fix-plan-blank-line-caret.md)。

### 验证

| 探针 | 内容 | p5 错 | 修复后错 | 回归 |
|---|---|---|---|---|
| `probe56` | 目标形状，28 点 | 1（`T1@0`，+26px） | **0** | — |
| `probe57` | 8 形状 × 97 点 | 17 | 15 | **0** |

**回归 = 0**：无任何"p5 原本正确、修复后却错"的点。

### 现场录制核对

用户提供一份完整会话录制（346s / 38035 帧 / 1775 事件 / `errors: []`）：

- 异常 17 条 = 16 × `nativeNoGeometry` + 1 × `cometOffset`；
- **静止态（折叠且双向稳定 200ms）中 `|dY| ≥ 3` 的帧 = 0**（最大 0.38px）；
- 零几何连续段（≥200ms）35 段中，**31 段命中修复后公式 `br+24`，0 段命中 p5 旧公式 `span+2`**；
- 唯一 `cometOffset`（`dY = −312` = 13 行）上下文是**鼠标拖选 + 滚动**，不是键盘空行路径。

> ⚠️ 该录制跑的是**已含修复**的构建（`lib/client.js` = `EC6806C7…`），只能作为"修复后未再出现"的旁证，**不能**证明旧缺陷存在。

### 被推翻的旧机制（保留以见思路演变）

| 旧断言 | 实际 |
|---|---|
| Case A（`childNodes[offset-1]` 是 `<br>`）抢先命中 `<p><br></p>` 空段落 | Case A 的入口 `focusNode instanceof Element` **从不成立**（焦点是 `#text`） |
| p5 落到 Tier 3 取"段内第一个 `<br>`"，跳回第一行 | 那个 `<br>` 是 span 的**兄弟**，`querySelector` 返回 `null`；真正错的是取到多行 span 的包围盒 |
| "DSH 的 `Enter` 产生段内连续 `<br>`" | 粘贴产生**字面 `\n`**；`Shift+Enter` 产生 `<span>` + `<br>` + `<span>` |
| "Lexical 用 element 锚点（`focusNode = <p>`）" | `focusNode` **永远是 `#text`** |

**教训**：早期探针用**手搓 DOM（`<br>` 串）**模拟输入框，而非真实 Lexical 生成的 DOM。在错误的 DOM 形状上可以得出自洽但无效的结论。

### 未解释的残留

用户曾报告"未分组行首按 `↑` 上不去"。录制中未见对应异常，**尚无定论**。

## 条目 B — 按 ← 后彗星光标落点错误（待复现确认）

**报告日期**：2026-10-13
**状态**：有待复现，代码级候选机制已定位
**证据等级**：**截图证据 + 代码结构推断**（未复现，未见录制证据）
**影响面**：主聊天输入框（`[data-composer-input]`，Lexical contenteditable）

### 现象

在存在"块内多行、行首有换行结构"的文本中，把光标放在某一行**行首**后按一次 `←`，光标本应直接落到**上一行的行尾**；但有时会先落到错误位置（`图一→图二→图四` 或 `图一→图三→图四`），**再按一次 `←` 才回到正确位置**。

用户已明确澄清：**不是动画路径问题**，是"按一下到上面，再按一下才正常"。

### 截图测量结果

四张截图（974×383 / 969×366 / 967×370 / 975×373）按内容平移对齐后，用光标精确色 `#4176E6` 定位：

| 图 | 光标 x | 光标 y | 所在行 | 角色 |
|---|---|---|---|---|
| 图一 | 23 | 198..216 | `未分组` 行行首 | 起点 |
| 图二 | 24 | 19..37 | `→ related links 段` 行（**整块第一行**） | 错误落点 A |
| 图三 | 20 | 166..184 | `⇕ 8px` 行**行首** | 错误落点 B |
| 图四 | 93 | 169..187 | `⇕ 8px` 行**行尾** | 正确落点 |

**图二 距起点约 174px、跨约 7 个文本行**，远超任何缓动插值帧的移动范围——因此它是**真实的测量输出**，不是动画中间帧。

注：图三（x≈20）与图二（x≈24）的横坐标都落在**内容区左边缘**；图四（x≈93）才紧贴 `8px` 文字右侧。这个 x 分布与回退分支的返回值对应。

### 候选机制（高置信度，但未复现）

`measureRichCaret()` 是分层回退结构。**一旦 Tier 1 取不到可用矩形，后续各层返回的都不是真实插入点**：

- **`lineStartLeft`**（内容区左边缘）→ 对应**图三**（x≈20）。Case A / Case B 都以它作为 `left` 返回。
- **宿主原点 / 块内第一个 `<br>`** → 对应**图二**（整块第一行）。Tier 3 的 `querySelector('br')` 或 Tier 4 的宿主 padding 兜底都会给出这个坐标。

**结论**：图二与图三恰好是这套回退逻辑的两个输出坐标。因此根因是**测量回退层给出的不是真实插入点**，而非缓动动画。

> **与条目 C 的关系**：同源——都发生在 Tier 1 取不到矩形、改走回退分支的时刻。条目 C 的修复（Case C）只覆盖了"文本节点 + 紧接 `<br>`"这一种形态；条目 B 的场景涉及**行首**位置，可能落在 Case C 的 `\n` guard 之外，**需单独核查是否已被覆盖**。

### 待确认项

1. **复现**：能否稳定重现"按一下错、再按一下对"。
2. **是否已被 Case C 覆盖**：在条目 B 的具体形态下，`focusNode` 是否为文本节点、是否紧接 `<br>`。
3. 错误落点是"稳定保持到下一次按键"，还是"仅一瞬后自愈"。
4. 触发是否与行首/块边界处的 `<br>` 或行内元素（`<code>` 等）相邻有关。

### 复现时要采集的数据

用已有的通用录制器（`probe-caret-recorder-v4.js`）录制，它会逐帧记录原生/彗星位置与差值，并自动标记异常：

```js
__CP.mark('条目B开始');   // 在按 ← 之前打标记
// …按 ←…
__CP.report();            // 看异常清单
__CP.save();              // 导出 JSON
```

关键判据：`anomalies` 里是否出现 `cometOffset`，且其上下文是否为**键盘路径**（非拖选）。

## 条目 A — 输入光标"不跟手"（未复现，待验证）

**报告日期**：2026-10-07（2026-10-13 复看时未能复现，2026-10-13 完整录制中亦未出现）
**状态**：观察中，无定论
**证据等级**：**无可复现证据**
**影响面**：曾报告为提问卡片的自定义回答框（`[data-question-key] textarea`）

### 现象

打字时光标动画"慢一拍"才追上插入点，**文字上屏本身正常**。曾报告"越输入越长越明显"。用户明确表示：平时正常输入框不会，只在提问卡的自定义回答那里感觉明显。

### 已排除 / 已修正的判断

- ~~"主线程被阻塞导致光标掉帧"~~：与"文字上屏很干脆"矛盾。降级为**放大器**而非主因。
- ~~"掉帧是机器算力不足"~~：与实测配置（Ryzen 7 9700X / RX 7900 XT / 1920×1080@240Hz）矛盾，已作废。

### 仍成立的事实（代码级）

1. **缓动按帧计，无 delta-time**——每帧固定走剩余距离的 `COMET_SMOOTHNESS = 0.2`，`loop()` 丢弃了 rAF 的时间戳。因此**帧率直接决定光标速度**。对照：同一文件里的呼吸闪烁**是**按墙钟算的（用 `performance.now()`）——同一份代码两种时间基准，本身即不一致。
2. **两条测量路径成本差一个数量级**：
   - 主输入框 → `measureRichCaret()`：读 selection 的 `getClientRects()`，零 DOM 操作；
   - 旧 textarea 路径 → `measureTextareaCaret()`：每帧新建/插入/读取/删除镜像 DOM，含两次强制同步回流。
3. **240Hz 帧预算仅 4.17ms**，重路径更容易超支；高刷反而**放大**两条路径的差距。
4. **提问卡作答框的裁剪视口取错**：用 `closest('[data-input-scroll]')`，而卡片用的是 `[data-question-scroll]`，故该处恒为 `null`，裁剪矩退化为 textarea 自身盒子。此缺陷解释"光标被错误裁掉"，**不解释**"慢一拍"。

> 第 4 条与用户"只有提问卡那里明显"的观察方向一致，值得优先核查；但它解释的是裁剪而非滞后。

### 暂定结论

条目 A 目前**无可复现证据**，不修。若后续复现，优先怀疑"缓动按帧计"（它单独就能解释"文字正常但光标慢"这一不对称现象）。

## 附：通用录制器

`probe-caret-recorder-v4.js`（`C:\Users\Think\.agent\temp\lexprobe\`）是常驻录制探针，装一次即可长期使用：

- 逐帧记录：原生（被隐藏）光标位置 + 插件彗星位置 + 两者差值；
- 记录事件：按键 / 输入 / 粘贴 / 选区变化 / 点击 / 焦点 / 滚动 / IME；
- DOM 结构变化时快照；

- 只读：仅监听 + 包装 `fillRect`/`clearRect`（`__CP.off()` 可还原）。
